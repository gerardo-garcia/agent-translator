# AGENTS.md

Guidance for AI coding agents working in this repository. (`CLAUDE.md` is a symlink to this file.)

`agent-translator` converts AI agent definitions between AWS Bedrock Agents, GCP ADK, Azure Foundry Agent Service and Kagent (Oracle Agent Spec as interchange) by going through a common IR. README.md is the user-facing doc; DESIGN.md holds the design decisions — read the relevant section before changing behavior. **Everything in this repository is written in English** (code, comments, docs, commit messages); the maintainer may talk to you in Spanish, but never add Spanish text to the repo.

## Commands

```bash
uv sync --all-extras                 # dev env. NOTE: `uv sync --extra X` alone REMOVES the dev tools (pytest, ruff)
.venv/bin/pytest -q                  # whole suite (~25 s)
.venv/bin/pytest -q tests/test_bedrock.py::test_name   # single test
.venv/bin/ruff check .               # lint (line length 100)
.venv/bin/agent-translator --help    # translate | fetch | deploy | inspect | validate | ir-schema | list-platforms
```

Generated artifacts that tests check for staleness — regenerate when you change what they derive from:
- `schema/ir.schema.json`: `agent-translator ir-schema > schema/ir.schema.json` after touching `ir/models.py` (`tests/test_ir_schema.py` fails otherwise).
- `docs/MATRIX.md`: `uv run --extra dev --extra validate-azure --extra validate-agentspec python scripts/gen_matrix.py` (every fixture × target).
- `src/agent_translator/models/catalog_data.py`: generated by `scripts/gen_model_catalog.py` from a LiteLLM snapshot; don't hand-edit.

`tests/test_adk_real_loader.py` loads emitted ADK projects with the real `google-adk` and is skipped normally; google-adk cannot share a lock with the Azure extras (openai<3 vs 3.x), so run it with `uv run --all-extras --with "google-adk[extensions]" --with mcp pytest tests/test_adk_real_loader.py` (CI job `adk-loader`).

Optional extras gate tests via `importorskip`: `validate-azure`, `validate-agentspec`, `validate-bedrock` (botocore), `fetch-aws` (boto3), `fetch-azure`.

Emit YAML only through `yamlio.new_yaml()`: it quotes strings that YAML 1.1 readers (PyYAML, Go) would turn into booleans, e.g. `OFF`.

## Architecture

**Two-step translation through the IR.** `source file → Adapter.parse → AgentIR (+ Report) → Adapter.emit → target files`. `AgentIR` (`ir/models.py`, pydantic v2, `extra=forbid`) is the single model; adapters never talk to each other. Platform-specific data that has no IR field is kept in per-platform extension slots so same-platform round trips stay lossless.

**Adapters are plugins.** Each platform implements the `Adapter` protocol (`adapters/base.py`: `detect`, `parse`, `emit(ir, out, options)`) and is registered in `pyproject.toml` under the entry-point group `agent_translator.adapters`; `registry.py` loads them and autodetects by `detect()` (which must never raise). After adding or renaming entry points, re-run `uv sync` so metadata refreshes. Format variants are chosen with `-O key=value` options (e.g. Bedrock `format=cloudformation|sdk`, Azure `format=foundry|agent-framework`).

**Reports, not silent loss.** Every parse/emit returns a `Report` (`report.py`) of coded items with severity `info < warning < lossy < manual < error`; `--strict` fails on `lossy` or worse. Anything that can't be translated exactly must add a report item rather than be dropped quietly.

**Models are not portable.** `models/` holds a table of model families (vendor, size tier, per-host ids) and per-host config (`HOSTS`). Every adapter's `emit` starts with `adapt_ir(ir, host, options, rep)`, applying policy `-O model_policy=keep|rehost|tier` and emitting `model-*` report codes. Edit the table through the generator, not by hand.

**Three more plugin groups, same pattern.** `fetch/` (`agent_translator.fetchers`) reads an agent from a live platform into local files an adapter can parse; `deploy/` (`agent_translator.deployers`) creates one from emitted files. Each module takes an optional injectable `client`, which is how tests run without any account.
- Fetchers are strictly read-only (Bedrock `Get*/List*`, `kubectl get`, Azure `agents.get`) and never read Secrets.
- Deployers are create-only and dry-run by default: `plan()` is always computed and never changes anything; `apply()` runs only with `--apply` plus confirmation/`--yes`; existing objects/agents/stacks are errors, never overwritten; files with `REPLACE-WITH-…` placeholders are refused; Secrets are never created. Keep these invariants when editing — tests assert them (Stubber rejects un-queued AWS calls, the fake kubectl records every call).
- Bedrock deploys a CloudFormation stack from the emitted template (not the `format=sdk` request files).

**Bedrock specifics.** Inputs: CloudFormation `AWS::Bedrock::Agent`, or `GetAgent` API/CLI JSON (`bedrock/getagent.py` converts the camelCase API shape into the CFN-shaped template and reuses the same parser). `bedrock/sdk.py` renders `-O format=sdk` from the emitted CFN template into `NN-<Agent>-<op>.json` request files validated against botocore.

**Kagent** supports `v1alpha2` and `v1alpha3` (`kagent/v1alpha2.py`, `v1alpha3.py`, shared `common.py`); `tests/conftest.py` validates every emitted resource against the CRD schemas in `fixtures/kagent/crds/`.

## Tests and fixtures

- Fixtures in `fixtures/<platform>/` are official samples; synthetic ones are marked as such and every source is recorded in `fixtures/*/SOURCES.md` — keep that file in sync when adding fixtures.
- `tests/test_matrix.py` runs every fixture through every target (including back-parse); a new platform or option normally means adding it to its `SOURCES`/`TARGETS`.
- Per-platform helpers live in `tests/*_helpers.py`; goldens in `tests/golden/`.
- Cloud behavior is tested only with fakes (botocore `Stubber`, fake `kubectl`, fake Azure client). fetch and deploy were additionally verified once against real Azure and a real Kagent cluster (see `docs/VERIFICATION.md`); Bedrock fetch and deploy have never run against a real environment — say so rather than claiming otherwise.
